## 0. 为什么是 HRCUS-CD，以及它可能怎么失败

选它的理由（第 132 节实测，非文献转述）：

```text
self-IoU@8 = 0.6683，远低于 0.80 止损线；八数据集里第三低，
  正视数据集里仅次于 LEVIR（S2Looking 0.610 为侧视，几何已否）
GSD 0.5 m —— 与 LEVIR 相同，是唯一验证过几何可解的工作尺度
建筑变化 —— 与 LEVIR 同类目标，朴素中位直径 18.4 px
规模 11391 对，与 LEVIR 完全独立（不同课题组、地区、年份）
```

最强的一条实证理由：**HRCUS 的目标形态与 WHU 几乎相同**（面积加权中位
直径 92.9 vs 91.6 px），而 WHU 的任务收益是够的（headroom 0.10880，
除 LEVIR 外唯一过 0.05 的）。WHU 死在原生 0.075 m 的几何，而 HRCUS 是
0.5 m。**即 HRCUS ≈「WHU 的形态 + LEVIR 的 GSD」，该组合从未被测过。**

先验风险，写在前面：

```text
R1 瓦片仅 256x256 = 128 m 地面覆盖，LEVIR 是 1024 / 512 m。
   第 121 节已证覆盖是次要但真实的因素；定位器在 1024 上训练，
   GZ-CD 在 512 上零适配 pck2 已降到 0.844/0.530/0.291。
   **且该数据集以 256 瓦片分发，无法重新拼大，这个变量我们动不了。**
R2 标签代理是单向筛查（第 118.3 / 123.1 节）。S2Looking 代理 0.610
   比 HRCUS 还好，实测 headroom 仅 0.0330——检测器绝对精度低会
   独立地压掉 headroom。通过筛查只意味着未被排除。
R3 官方划分可能泄漏。DSIFN 的官方划分把同一 source crop 的增广副本
   分到 train 与 val（第 110.2 节），HRCUS 未经审计，风险同级。
R4 若 Gate 0 失败，需要能区分「HRCUS 的影像问题」与「256 瓦片本身
   太小」——见第 4 节的对照设计。
```

## 3. Gate −1：数据卫生与划分

### 3.1 审计项

```text
A1 尺寸/通道/标签二值性/无效样本 = 0        tools/audit_dataset.py
A2 cross-split 完全重复三元组 = 0
A3 增广泄漏（二面体哈希 + 感知哈希）        tools/audit_augmentation_leakage.py
A4 每个 parent_id 只出现在一个 split
```

**A3 是本关的重点。** 与 GZ-CD 不同，HRCUS 的划分不是我们生成的，
空间不相交没有构造保证，只能靠审计。DSIFN 正是栽在这里。

同时运行 `tools/audit_change_target_scale.py`，**并复算第 132 节的
92.9 px**——那个数是本机用 scipy 8-连通算的，cv2 不可用，口径应当一致
但未验证。**若与 92.9 不符，先查工具再谈数据，不得直接采信新值。**

### 3.2 若 A3 不通过

按 DSIFN 的做法用 `tools/build_source_crop_split.py` 做 source-crop
重划分，比例尽量贴近官方（70/20/10），并在报告里如实写明「官方划分
不可用」及其证据。**重划分后 test 仍然封存。**

### 3.3 A3 实际结果与已冻结的清洗规则（2026-07-29 补写，先于 Gate 0）

A3 触发了，但成因与 DSIFN 不同，因此 3.2 的重划分被**更小的**补救措施
替代。两类问题必须分开处理：

```text
退化瓦片：11388 中有 2000（17.6%）两个时相全黑、标签全零，是填充。
          它们互为字节相同，塌缩成同一个 canonical digest，
          单独制造出巨量伪跨划分泄漏。
真跨划分近重复：剔除退化瓦片后，差分哈希仍报 36288 对，
          但逐像素复核显示 **94.8% 是哈希碰撞**——64 位差分哈希
          在低纹理城市瓦片上饱和。经复核为真的只有 1897 对，
          去重后涉及 336 个样本，各划分约 4%，
          且其中 34.5% 本身是近均匀瓦片。
```

**冻结的清洗规则**（`tools/build_hrcus_clean_split.py`，阈值写死在报告里）：

```text
1. 丢弃两个时相都全零的样本；
2. 哈希候选对（hamming <= 5）必须通过逐像素复核
   （64x64 缩略图平均绝对差 < 3.0）才算真重复；
3. val 与 test 一律不重划、不丢弃；
4. 与 val 或 test 构成真重复的 train 样本丢弃。
```

第 3、4 条与 `tools/build_source_crop_split.py` 对 DSIFN 的做法一致：
保护评估划分的可比性，代价由训练集承担。

结果：

| split | 原始 | 清洗后 |
|---|---:|---:|
| train | 7974 | 6372 |
| val | 2276 | 1850 |
| test | 1138 | 948 |

**因此本数据集在论文中必须声明为「官方划分 + 记录在案的清洗」，
不是官方划分原样**，与 DSIFN 的 source-crop 划分同级披露。
17.6% 退化瓦片是数据集事实，须一并写明。

清洗后 val 的 change fraction 由 0.0223 修正为 0.0275（仅计有效瓦片）；
第 132 节的 self-IoU@8 = 0.6683 **不受影响**——全零标签对交并集
贡献均为 0。

## 4. Gate 0：无标签几何筛查（含瓦片尺寸对照）

零适配跑 HRCUS val，判据沿用 `configs/p15_dsifn_screening.yaml` 三分支：

| 分支 | 条件 | 动作 |
|---|---|---|
| 绿 | `D_excess <= +1.0` 且 `clean q <= 0.15` | 进 Gate 1 |
| 红 | `D_excess >= +3.0` **且** `clean q >= 0.40` | 止损 |
| 黄 | 其余 | 进 Gate 1 |

止损要求两信号同时红；单信号红属歧义，走决定性判据（第 71 节路由）。

**本关额外要求：同一次运行内产出两个 LEVIR 对照**，用于分离 R1 与 R4：

```text
C1 LEVIR center-crop 512 / tile 256  —— 已发布 clean q = 0.0625 的几何
C2 LEVIR center-crop 256 / tile 128  —— 与 HRCUS 完全同几何的对照
候选 HRCUS val 原生 256 / tile 128
```

HRCUS 只有 256 px 图幅，要让卫生诊断有多于一个瓦片，tile 必须取 128；
对照因此也必须是 256/128。C1 取 512/256 而非原生 1024，是因为
**0.0625 这个已发布数字就在 512/256 这个几何上**——C1 同时充当
第 85 节要求的仪器自检：**C1 复现不了 0.0625，本轮作废，不读候选。**

预注册读法（写在结果之前）：

```text
C2 与 C1 接近，而 HRCUS 明显更差  → 问题在 HRCUS 影像本身
C2 自己就超过 clean q 绿线        → 256 窗口本身就压不住定位；
                                    候选分数不可单独归因，且绝对
                                    clean q 门槛已离开其标定尺度，
                                    该分支按歧义（黄）读，不按红读
两者都劣化且程度相当             → 混合，两者都报
```

最后一条不是新开的宽松口子，而是第 71 节既有路由（歧义走决定性判据）
的应用；判据形式与触发条件都在跑前写死在
`configs/p20_hrcus_screening.yaml` 里。这条对照是 R4 的唯一解法：
没有它，Gate 0 一旦失败就无法归因。

## 5. Gate 1：决定性判据 headroom

```text
判据：Shift-8 input-oracle headroom >= 0.05        （门槛不变）
参照：LEVIR 0.2141 / WHU 0.10880 / GZ-CD 0.05236 /
     S2Looking 0.0330 / DSIFN 0.0227
支撑：raw 与 oracle 必须在对称交集有效像素上评分（第 114 节的教训）
```

同时如实报告余量。GZ-CD 是 +0.0024 的边际通过（109 个 val 瓦片上属噪声），
**若 HRCUS 也落在 +0.005 以内，必须与结论一同报告为边际，不得当作稳健通过。**
HRCUS val 有 2277 个瓦片，比 GZ-CD 的 109 个稳定得多，这一点对本关有利。

失败 → 止损，写成「HRCUS 在输入级可恢复空间不足」的限制。

## 6. Gate 2：全链复刻与四门槛

```text
链路：P3b → 输入级定位器 stage A → q 头全分辨率校准 → P7-3 分类器
     stage A **必须传 --initial-checkpoint**（第 122.2 节的作废教训）
守卫：stage A 训完立刻核对 val F1 是否复现 Gate 1 的 clean F1（容差 0.05），
     不符即退出，下游数字不可读
primary = safe_veto_task，搜索半径固定 4
划分：按 parent_id 做 fit / early-stop / risk-calibration 三段
```

四条门槛与 LEVIR / seed-1234 / GZ-CD **完全相同，不得放宽**：

| 门槛 | 要求 |
|---|---|
| clean F1 掉幅 | <= 0.001 |
| shift mean F1 增益 | >= 0.020 |
| Shift-8 F1 增益 | >= 0.050 |
| Shift-8 oracle 恢复率 | >= 0.50 |

### 6.1 跑前必须落盘 ceiling_guard.json

沿用 GZ-CD 的做法（第 122.1 节）：**在 Gate 2 之前**用 Gate 1 的 oracle
天花板与上表并列，落盘记录两条绝对门槛是否算术可达。这样结果无法被
事后重新解释。

**若门槛不可达**，仍然照跑，但结论写成「门槛在该数据集上不可达」而非
「方法无效」——这正是 GZ-CD 那一轮唯一有价值的产出。

### 6.2 捕获率：报告量，非门槛，判读带跑前写定

```text
捕获率 = router gain / oracle gain，对 mean 与 Shift-8 分别报告
参照：LEVIR seed-3407 73.0% / 65.2%，seed-1234 87.5% / 83.4%
     GZ-CD 12.9% / 8.4%

>= 65%      → 方法在该数据集上迁移成立
40%–65%     → 部分迁移，须与 GZ-CD 的 12.9% 一同报告，不得只提本数
20%–40%     → 迁移弱
< 20%       → 与 GZ-CD 同类，第二正例线正式关闭，不再重开
任一档出现 Shift-2 捕获率为负 → 排序反转，按第 V-C 节口径报告
```

**第 120.6 节建议把 Gate 2 改写成相对捕获率。本协议不采纳为门槛**，
理由是：改判据会破坏与 LEVIR / GZ-CD 的可比性，且在自己想要通过的时候
放宽形式，无论理由多充分都会削弱全部预注册纪律。捕获率只作报告量。

## 8. 失败即结论

任一关失败都不是浪费：

```text
Gate −1 失败 → 官方划分不可用的又一实例，与 DSIFN 并列
Gate 0  失败 → 结合 C2 对照，给出「分析窗口下限」的定量边界，
              这是第 121 节 GSD 结论的正交补充
Gate 1  失败 → 「WHU 的形态 + LEVIR 的 GSD」仍不足以产生任务收益，
              直接反驳第 0 节那条最强的推进理由，价值很高
Gate 2  失败 → 第二正例线关闭；若捕获率 < 20%，方法侧瓶颈由单例升为两例
```

**不得因为任何一关的结果去调整门槛、primary、搜索半径或瓦片尺寸。**
